# Zed

## Keybindings

Zed keybindings are defined in a JSON `keymap.json` file as an array of binding groups. Each group can contain a `bindings` object, an optional `context` expression, and optional keyboard-layout behavior such as `use_key_equivalents`.

### tl;dr

- Modifiers: `ctrl-`, `cmd-`, `win-`, `super-`, `alt-`, `shift-`, `fn-`, and `secondary-`.
- Shortcuts: one keypress string such as `cmd-k` or `ctrl-right`.
- Chords: supported; separate successive keypresses with spaces, for example `cmd-k cmd-s` or `j k`.
- Conditions: expressed with the group's `context` string, using Zed's context tree and boolean operators.
- Args: supported; actions can be bound as arrays such as `["workspace::ActivatePane", 0]` or `["pane::DeploySearch", { "replace_enabled": true }]`.
- Platform: no dedicated per-binding platform field in `keymap.json`; platform differences are usually expressed with key names like `cmd-` vs `win-`, the `secondary-` alias, or context clauses such as `os == macos > Editor`.
- Removal: bind a key sequence to `null` to disable it in a given context.
- Extension bindings: the public extension docs do not describe a general API for extension-defined actions or keymap contributions.
- Other features: predefined base keymaps, a built-in keymap editor, `use_key_equivalents` for some non-QWERTY layouts, `workspace::SendKeystrokes` for remapping a shortcut to a sequence, and `terminal::SendKeystroke` for forwarding keys into the terminal.

### Keymap shape

```ts
type ZedActionBinding = string | null | [string, unknown];

type ZedKeymapEntry = {
  context?: string;
  use_key_equivalents?: boolean;
  bindings: {
    [keySequence: string]: ZedActionBinding;
  };
};

type ZedKeymap = ZedKeymapEntry[];
```

In practice, the string value is usually an action name such as `zed::OpenKeymap` or `editor::SelectLargerSyntaxNode`. Arrays are used for actions that take arguments, and `null` disables a binding.

### User keybinding file

Zed stores user keybindings in `keymap.json`:

- macOS/Linux: `~/.config/zed/keymap.json`
- Windows: `~\\AppData\\Roaming\\Zed/keymap.json`

The file is edited directly or through the keymap editor. `zed: open keymap file` opens the JSON file, and `zed: open keymap` opens the graphical editor. Changes made in the keymap editor are reflected back into `keymap.json`.

### Properties

- `context` **{string}**: Optional context expression that determines when the binding group is active.
- `use_key_equivalents` **{boolean}**: Optional keyboard-layout setting for matching certain non-QWERTY key equivalents.
- `bindings` **{Object}**: Maps key sequences to actions, action arrays, or `null`.
- `[keySequence]` **{string | null | [string, unknown]}**: The action to run for that key sequence, or `null` to disable it.

### Basic examples

Basic bindings:

```json
[
  {
    "bindings": {
      "cmd-k cmd-s": "zed::OpenKeymap",
      "ctrl-right": "editor::SelectLargerSyntaxNode"
    }
  }
]
```

Context-specific bindings:

```json
[
  {
    "context": "ProjectPanel && not_editing",
    "bindings": {
      "o": "project_panel::Open"
    }
  },
  {
    "context": "Editor && mode == full",
    "bindings": {
      "secondary-/": "editor::ToggleComments"
    }
  }
]
```

Bindings with arguments:

```json
[
  {
    "bindings": {
      "cmd-1": ["workspace::ActivatePane", 0],
      "cmd-shift-f": ["pane::DeploySearch", { "replace_enabled": true }]
    }
  }
]
```

Disabling and remapping:

```json
[
  {
    "context": "Workspace",
    "bindings": {
      "cmd-r": null,
      "alt-down": ["workspace::SendKeystrokes", "down down down down"]
    }
  },
  {
    "context": "Terminal",
    "bindings": {
      "ctrl-n": ["terminal::SendKeystroke", "ctrl-n"]
    }
  }
]
```

### Key sequence syntax

Each key in `bindings` is a sequence of one or more keypresses separated by spaces. Each keypress is written as modifiers followed by a key name or character.

- `cmd-k cmd-s` means press `cmd-k`, then `cmd-s`.
- `space e` means type `space`, then `e`.
- `shift shift` is valid and matches pressing and releasing `shift` twice.

Zed supports named keys such as `tab`, `f1`, and `cmd`, as well as Unicode characters generated by the keyboard. `alt-` and the produced character can both work for the same physical combination on some layouts. For example, `alt-c` on a US macOS keyboard produces `ç`, and Zed documents `alt-c` as the conventional spelling.

One important quirk: `shift-` only works with letters to mean the uppercase form, such as `shift-g` for `G`. It is not used to describe punctuation that requires Shift on a physical keyboard.

### Contexts and scopes

Zed does not use selectors. It scopes bindings with a `context` expression evaluated against the active context tree.

The tree starts at `Workspace` and descends into panes, panels, editors, terminals, and other UI nodes. The main debugging tool is `dev: open key context view`, which shows the active tree and attributes at the current focus point.

Context expressions support:

- `X && Y` and `X || Y`
- `!X`
- `(X)` for grouping
- `X > Y` to match an ancestor/descendant relationship in the context tree
- attribute checks such as `mode == full` or `os == macos`

Examples:

- `"context": "Editor"` matches any editor, including inline inputs.
- `"context": "Editor && mode == full"` matches full editors used for normal editing.
- `"context": "!Editor && !Terminal"` matches anywhere outside focused editors and terminals.
- `"context": "os == macos > Editor"` matches editors on macOS.

Attributes only exist on the node that defines them. A condition that combines debugger state with Vim state must account for the tree, for example `debugger_stopped > vim_mode == normal`.

### Actions, arguments, and precedence

Almost all Zed functionality is exposed as actions. Keybindings usually map directly to action IDs such as `editor::ShowCompletions` or `language_selector::Toggle`.

Actions can be bound in three main ways:

- string action IDs for actions without arguments
- `[action, value]` arrays for one positional argument
- `[action, object]` arrays for structured arguments

When several active bindings match the same keystroke:

- the binding on the lower node in the context tree wins
- if the competing bindings are on the same level, the later definition wins

That second rule is what makes user keymaps override the built-in keymaps.

Zed also resolves prefix conflicts for multistep bindings. If one active binding is a prefix of another, Zed waits 1 second after the shorter sequence to see whether more keys follow.

### Non-QWERTY keyboards and key equivalents

Zed documents explicit non-QWERTY behavior and treats it as a first-class part of the keybinding system.

- On macOS, Zed can match against both the ASCII equivalent and the actual produced key for many layouts.
- On Linux, non-ASCII-producing keys use their QWERTY-layout equivalent for shortcut matching starting with Zed v0.196.0.
- `use_key_equivalents` can be enabled per binding group to opt into layout-based matching for personal bindings.

Example:

```json
[
  {
    "use_key_equivalents": true,
    "bindings": {
      "ctrl->": "editor::Indent"
    }
  }
]
```

### Extension and plugin keybindings

Zed's public extension documentation covers language extensions, debugger extensions, themes, icon themes, snippets, slash commands, agent server extensions, and MCP server extensions. It does not document a general extension API for registering arbitrary actions or contributing keybindings to `keymap.json`.

In practice, user keymaps target Zed actions, built-in modal layers such as Vim or Helix mode, and task actions defined elsewhere in the editor. If an extension exposes functionality through documented Zed actions, those actions can be bound like any other action. The public docs do not describe extension-specific fields analogous to `command`, `when`, `args`, selector scopes, or per-extension keybinding manifests.

### Additional notes

- `base_keymap` can switch the default keybinding layer to presets such as VS Code, Atom, Emacs, JetBrains, Sublime Text, TextMate, Cursor, or `None`.
- `vim_mode` and `helix_mode` add modal bindings on top of the base keymap. Helix mode uses the same context system as Vim mode.
- `workspace::SendKeystrokes` can remap one shortcut to a sequence of simulated keystrokes, but it does not wait for asynchronous actions and is limited to 100 simulated keys.
- Task shortcuts can also be bound to tasks defined in `tasks.json`.
